# Expectation Templates

How the Stage 2.1 expectation-builder turns live API data into
`visual_expectation` strings that the multimodal verifier checks against
each screenshot. One expectation string per test, under 200 chars.

## Principles

- **Be specific with numbers, loose with formatting.** The verifier should
  accept `₹18,00,000`, `₹18 L`, `18,00,000`, `18.00 L` — do not over-specify
  the rendering. Write `"Annual CTC ≈ ₹18,00,000"` not `"Exactly ₹18,00,000"`.
- **Include a floor/ceiling when exact value is unstable.** For derived
  calculations (FIRE number, health score, DTI), say `"FIRE number between
  ₹2 Cr and ₹2.5 Cr"` if your computed value is `₹2.2 Cr` ± 15%.
- **State what must be visible, not what is absent.** Avoid `"No NaN"` —
  the generic AI check already catches NaN/undefined/empty rendering.
- **One line per expectation.** Keep strings short — the verifier is making
  a single judgment, not parsing a checklist.
- **Use the actual displayed format.** Rupee-sign + Indian grouping is what
  the app renders, per `src/utils/formatters.ts`. Don't write `"$18,000"`.

## Template Patterns by Test Type

### Formula verification (`10-formula-verification.spec.ts`)

```
"{Primary metric name} ≈ {formatted value}; {secondary fields as a short list}"
```

Example — fire-goals:
```
"FIRE number ≈ ₹3.5 Cr; years to FIRE between 12 and 18; savings rate ≈ 42%"
```

Example — liabilities:
```
"Total outstanding ≈ ₹28,50,000; monthly EMI ≈ ₹42,000; DTI ≈ 28%"
```

Example — tax-planning:
```
"Old regime tax ≈ ₹1,85,000; new regime tax ≈ ₹1,95,000; old regime saves ₹10,000"
```

### Navigation (`01-navigation.spec.ts`)

```
"{Section} page heading visible; tab '{expected active tab}' selected;
 FY selector shows {fy}; at least N primary cards visible"
```

Example — salary:
```
"Salary page visible; 'Overview' tab selected; FY 2025-26; 4 summary cards"
```

### CRUD operations (`02-*` or `11-*`)

```
"{Count} rows in the {entity} table; newly-created '{name}' row visible;
 total amount ≈ {formatted total}"
```

Example — expenses CRUD:
```
"5 expenses in table; 'Grocery Test 2026-04' row visible; total ≈ ₹3,450"
```

### Cross-page consistency (`25-*`)

```
"'{Metric name}' on this page ({formatted value}) matches same metric on {other page}"
```

Example — fire-integration:
```
"Total investments on fire-goals (₹15,75,000) matches total on investments page"
```

### Data setup (`00-data-setup.spec.ts`)

```
""   (empty — data setup tests have no meaningful UI to verify;
 /e2e-visual-run falls back to generic visual check)
```

### Empty state tests (when section has no data)

```
"Empty state card visible with '{section} not yet configured' message;
 CTA button to add first entry visible"
```

## Building Strings from API Data

### Step 1: Unwrap the envelope

```bash
# Response: { "success": true, "data": { ... } }
value=$(curl -s -H "x-dev-bypass: true" http://localhost:3000/api/fire/metrics | jq -r '.data.fireNumber')
```

### Step 2: Format as INR via app logic

The verifier accepts any of the three formatters from
`src/utils/formatters.ts`:

| Value | formatINR | formatINRLakhs | formatINRCompact |
|-------|-----------|----------------|-------------------|
| 15000000 | ₹1,50,00,000 | 1.50Cr | 1.50 Cr |
| 525000 | ₹5,25,000 | 5.25L | 5.25 L |
| 8300 | ₹8,300 | 8.3K | 8.3 K |

The expectation string can use **any** of these — the multimodal verifier
recognizes all three. Prefer `formatINRCompact` (e.g., `≈ ₹1.50 Cr`) for
values above 1 lakh — reads easier.

### Step 3: Add tolerance words for derived values

For values that depend on compound calculations, add a tolerance clause:

```
"FIRE number ≈ ₹3.5 Cr (± 10%)"
"Monte Carlo success rate between 75% and 90%"
```

### Step 4: Write to visual-tests.yml

```yaml
# visual-tests.yml — auto-generated by iterative-visual-test-pipeline, section: fire-goals
expectations:
  'e2e/tests/fire-goals/10-formula-verification.spec.ts::verify FIRE number calculation':
    'FIRE number ≈ ₹3.5 Cr (± 10%); annual expenses ≈ ₹18,00,000; SWR shown as 3.5%'
  'e2e/tests/fire-goals/01-navigation.spec.ts::display overview tab':
    'FIRE Goals page visible; Overview tab selected; 4 metric cards; freedom score 0-100'
```

The top-level `expectations` key is a flat map from
`{file_path}::{test_name}` → expectation string. The key format matches
Playwright's test-id format (file path + test title).

## What NOT to Put in Expectation Strings

- **Exact rupee amounts for stored values.** Stored data evolves. Use `≈`
  or ranges.
- **Timestamps, dates, or "last updated" strings.** These vary every run.
- **User names, avatars, or any PII.** Masked by visual config.
- **CSS-specific wording.** Don't say `"blue button"` — say `"primary CTA"`.
- **Multiple independent checks in one string.** If a screenshot needs
  verification of 5 separate things, the test itself is probably doing
  too much — let the verifier catch one clear failure instead of diluting
  the expectation.

## Fallback — When No Expectation Is Built

When the expectation-builder can't map a test to a specific API value
(e.g., hover interaction tests, keyboard navigation tests, tests for UI
behavior that isn't data-dependent), LEAVE THE EXPECTATION EMPTY.

`/e2e-visual-run` then uses generic AI verification (no error dialogs, no
NaN/undefined, layout correct, data populated if the view is expected to
have data). Per `/verify-screenshots` strategy order: baseline > text hint >
generic AI, the empty-expectation tests just skip the "text hint" step.

This is preferable to fabricating a weak expectation. A specific-but-wrong
expectation is worse than no expectation at all — it will either produce
false failures (noisy) or get watered down to the point of being useless.
