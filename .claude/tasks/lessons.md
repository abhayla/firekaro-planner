## 2026-06-04 — A GitHub issue's literal suggested fix would have introduced a BIGGER bug (#29)
**Finding:** Fixing #29 (let-out rental taxed gross — Sec 24(a) 30% deduction missing), the issue body's suggested fix was "apply 0.7 to `otherTaxable`." Tracing the data flow first showed that `otherTaxable` feeds BOTH `annualIncome.total` (the CASH basis → `annualSavings`) AND the tax `grossIncome`. Multiplying it by 0.7 would correctly cut tax but silently drop 30% of **real rent received** from savings — a *larger* error (₹72k/yr cash vs ₹24k/yr tax for the worked example), pushing FIRE later. Both the FinTech analyst and code review confirmed the divergence was the right call.
**Root cause / pattern:** The 30% standard deduction is a TAX fiction — the landlord receives full cash; only the taxable basis shrinks. The correct fix separates cash-vs-taxable: keep rental FULL in the cash total, subtract the 24a deduction from the tax `grossIncome` only (+ net the bridge rental cash at `gross·(1−mr·0.7)`). **An issue's suggested fix is a hypothesis, not gospel** — for financial math, ALWAYS trace where a value flows (cash basis vs tax basis vs cash-flow) before applying it.
**Gate-gap:** existing tests asserted FIRE-age sanity (shape) but nothing asserted let-out rental enters taxable income net of 30% — a shape-vs-substance miss. **Closed by** a *deterministic* differential test (`derive.spec.ts` #29: Rental-vs-Interest, asserts cash-total-equal + rental-taxed-less + saving bounded by the deduction) — a CI test, the good kind per the gate-gap retro below. ## 2026-06-09 — A global CSS override of a Vuetify component default silently lost the cascade (needs !important)
**Context:** #77 tooltip-contrast fix. Wired a global `VTooltip { contentClass: "fk-tooltip" }` default + a `.v-overlay__content.fk-tooltip { background:#1e293b; color:#fff; ... }` rule in `tokens.css`. The class applied, the rule was in the CSSOM, `opacity:1 !important` took — but the **first in-browser render was STILL washed out**: computed `background: rgb(245,247,250)` (surface-variant), `color: rgb(238,238,238)`. The un-`!important` `background`/`color`/`border-radius`/`padding` lost.
**Root cause:** Vuetify ships its own `.v-tooltip .v-overlay__content` rule at the SAME specificity (0-2-0) as `.v-overlay__content.fk-tooltip`, and Vuetify's stylesheet loads AFTER `tokens.css`, so at equal specificity source-order hands Vuetify the win. Only the `!important` declaration (opacity) survived.
**Fix/Pattern (GENERIC):** when overriding a Vuetify component's default visual styling from `tokens.css`, the plain declaration loses the cascade. Use either (a) `!important` on the competing visual props (consistent with this file's existing `.v-application .text-medium-emphasis { ...!important }` override), or (b) a higher-specificity selector. **Caveat on (b):** `.v-application .<sel>` is the textbook fix BUT Vuetify teleports overlay content (tooltip/menu/dialog) into a `.v-overlay-container` whose ancestry under `.v-application` is NOT guaranteed — so a `.v-application`-prefixed selector can match NOTHING and silently re-break an overlay. For teleported overlays, `!important` is the safer lever; verify in-browser either way.
**Gate-gap:** the **static regression spec passed** asserting `background:#1e293b` even when it didn't render — a static-content lock CANNOT catch a cascade loss. The **in-browser Rule-24 render check** (computed-style read) is what caught it. Lesson: for any CSS override of a 3rd-party component default, the lock must be paired with an in-browser computed-style assertion, OR the static spec must assert `!important` (now done) AND a human/agent must confirm the rendered computed value. Candidate `chart-theme-system.md` / `vuetify-conventions.md` note: "global overrides of Vuetify component defaults need `!important` (equal-specificity + later source order); verify the rendered computed style, not just that the rule exists." Status: PARTIAL (fixed + spec tightened to lock `!important`; the prose rule note is a proposal).

## 2026-06-09 — A static template-source regression spec asserting `<tag attr>` with a trailing `>` is brittle to additive attributes
